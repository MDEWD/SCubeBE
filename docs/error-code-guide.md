# 错误码说明文档

## 错误码定义

系统使用统一的错误码体系，所有错误码定义在 `ErrorCode` 枚举中：

| 错误码 | 说明 | 使用场景 |
|--------|------|----------|
| 0 | 操作成功 | 请求成功时返回 |
| 40000 | 参数错误 | 请求参数验证失败、参数格式错误等 |
| 40100 | 未登录 | 需要登录但未提供Token或Token无效 |
| 40300 | 无权限 | 用户没有权限执行该操作 |
| 40400 | 数据不存在 | 查询的数据不存在 |
| 50000 | 系统内部异常 | 未预期的系统异常、数据库连接失败、Redis连接失败等 |
| 50001 | 操作失败 | 业务操作失败（如删除失败、更新失败等） |

## 错误码返回格式

所有错误都使用统一的响应格式：

```json
{
  "code": 50000,
  "message": "系统内部异常",
  "data": null
}
```

## 50000 错误详解

### 什么时候会出现 50000 错误？

**50000 是系统内部异常错误码**，通常在以下情况出现：

1. **未捕获的运行时异常**
   - 空指针异常（NullPointerException）
   - 数组越界异常（ArrayIndexOutOfBoundsException）
   - 类型转换异常（ClassCastException）

2. **数据库相关异常**
   - 数据库连接失败
   - SQL执行错误
   - 数据库表不存在

3. **Redis相关异常**
   - Redis连接失败
   - Redis操作超时

4. **第三方服务异常**
   - 微信API调用失败
   - 其他外部服务调用失败

5. **配置错误**
   - 配置文件错误
   - 依赖注入失败

### 如何排查 50000 错误？

#### 1. 查看服务器日志

50000 错误会在控制台输出详细的异常堆栈信息：

```
系统异常：
java.lang.NullPointerException
    at com.scube.scubebackend.service.impl.UserServiceImpl.login(UserServiceImpl.java:68)
    ...
```

#### 2. 常见问题排查

**问题1：Redis连接失败**

**现象：** 日志显示 `RedisConnectionException` 或 `Connection refused`

**解决：**
- 检查Redis服务是否启动
- 检查 `application.yml` 中的Redis配置
- 检查Redis端口是否正确

**问题2：数据库连接失败**

**现象：** 日志显示 `SQLException` 或 `CommunicationsException`

**解决：**
- 检查MySQL服务是否启动
- 检查数据库配置是否正确
- 检查数据库是否存在
- 检查数据库表是否已创建

**问题3：空指针异常**

**现象：** 日志显示 `NullPointerException`

**解决：**
- 查看堆栈信息，定位到具体的代码行
- 检查对象是否为null
- 添加空值检查

**问题4：JWT生成失败**

**现象：** 日志显示JWT相关异常

**解决：**
- 检查JWT配置是否正确
- 检查secret key是否配置

### 改进建议

为了更好的调试，建议：

1. **查看完整日志**：50000错误会在控制台输出完整的异常堆栈
2. **添加详细日志**：在关键位置添加日志输出
3. **使用try-catch**：在可能出现异常的地方添加异常处理

## 错误处理流程

```
请求 -> Controller -> Service -> 异常
                              ↓
                    GlobalExceptionHandler
                              ↓
                    BaseResponse.error()
                              ↓
                    返回给前端
```

## 开发环境 vs 生产环境

### 开发环境
- 返回详细的错误信息（包括异常消息）
- 便于调试和定位问题

### 生产环境
- 只返回通用错误信息
- 不暴露系统内部细节
- 详细错误记录在日志中

## 最佳实践

1. **使用业务异常**：对于可预期的错误，使用 `BusinessException`
2. **提供友好提示**：错误消息应该对用户友好
3. **记录详细日志**：异常信息应该完整记录在日志中
4. **避免暴露敏感信息**：生产环境不要返回系统内部错误详情
